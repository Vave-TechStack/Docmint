# Verification/Reset Token Lookup — Design and Implementation

**Status:** IMPLEMENTED on `remediation/docx-and-product`. Migration written,
**not applied to any environment**.
**Date:** 2026-10-10
**Scope:** `verify-email` and `reset-password` token resolution.
**Migration required:** Yes (additive — see Rollout).

---

## 1. Current implementation and its limits

`VerificationToken.token` stores a **bcrypt hash**. Bcrypt is deliberately
non-deterministic and salted, so a hash cannot be searched by its input. The
owning row therefore cannot be recovered with an indexed lookup.

Both consuming routes work around this with a bounded sweep
(`src/app/api/auth/verify-email/route.ts:58`,
`src/app/api/auth/reset-password/route.ts:49`):

1. `findMany({ where: { expires: { gt: now } }, take: 50, orderBy: { expires: 'desc' } })`
2. `bcrypt.compare(presentedToken, candidate.token)` for each row, first hit wins.

### What this buys

The sweep caps the worst case. An unauthenticated caller cannot force
unbounded bcrypt work: at most 50 comparisons (~250 ms each on typical
hardware) per request, behind a per-IP rate limit of 10/min. Without the cap,
each request would cost O(unexpired tokens across **all** tenants) × bcrypt,
and the table grows monotonically because expired rows are never pruned.

### What this costs

**1. Correctness — valid tokens beyond the 50th row are rejected.**
The `take: 50` is applied before the comparison, so a legitimate token that
sorts past the window is reported invalid with an indistinguishable `400`.
Users affected: any account whose verification/reset token is not among the 50
most-recently-expiring unexpired tokens platform-wide. This is reachable in
normal operation — the table accumulates a row per forgot-password,
resend-verification and signup, and nothing prunes expired rows, so the 50th
newest token is not a high bar on a busy instance.

**2. Ranking is arbitrary from the user's perspective.** `expires desc` is
newest-expiring-first, not most-recently-created-first, so which tokens fall
inside the window depends on token TTLs rather than on when the user asked.

**3. Latency.** A legitimate user near the window boundary pays up to 50
bcrypt operations before matching.

### Severity

This is a **capacity/availability defect, not an authorization bypass**. The
failure direction is safe: an unmatched token is rejected, never accepted.
An attacker cannot use the truncation to gain access — at worst it lets them
avoid work, which the rate limit already bounds. It is reported here because
it silently denies legitimate users, and because it is the kind of defect that
surfaces as "users say their reset link doesn't work" rather than as an error.

## 2. Proposed design: indexed HMAC lookup column

Add a deterministic, keyed digest column and search on that instead of
sweeping.

### Schema addition

```prisma
model VerificationToken {
  identifier String
  token      String   @unique   // bcrypt hash — unchanged, still the source of truth
  tokenIndex String?  @unique   // HMAC-SHA256(lookupSecret, token); null for legacy rows
  expires    DateTime
  purpose    String?             // 'verify' | 'reset' (see §4)

  @@unique([identifier, token])
  @@map("verification_tokens")
}
```

### Lookup algorithm

At issue time (forgot-password, resend-verification, signup):

```ts
const token = `r_${randomBytes(32).toString('hex')}`;
await prisma.verificationToken.create({
  data: {
    identifier: email,
    token:      await hashToken(token),   // bcrypt, unchanged
    tokenIndex: tokenIndexFor(token),    // HMAC-SHA256, indexed, unique
    expires:    new Date(Date.now() + TTL),
    purpose:    'reset',
  },
});
```

At verification time:

```ts
const candidate = await prisma.verificationToken.findUnique({
  where: { tokenIndex: tokenIndexFor(presentedToken) },
});
if (!candidate) return reject();
if (candidate.expires <= new Date()) return reject();
if (!await verifyTokenHash(presentedToken, candidate.token)) return reject();
```

One indexed read, one bcrypt comparison (the bcrypt check is retained as the
authoritative verification — the HMAC only *locates* the row).

### Why HMAC-SHA256 and not a plain hash

A bare SHA-256 of the token would be indexed and fast, but verification tokens
are 32 bytes of CSPRNG output delivered by email. If an attacker obtains the
table via any read-only DB compromise, a plain digest lets them mount an
**offline dictionary attack** for tokens that were not generated by a CSPRNG
(for example any future low-entropy or user-derived token), and — more
immediately — lets them confirm a guessed token with one indexed lookup and no
bcrypt work, which converts the current ~250 ms-per-guess into ~1 ms.

Keying the digest with a server-side secret removes that property: the
digest is useless without `AUTH_SECRET`, so a table dump alone yields nothing
usable. Cost: rotating `AUTH_SECRET` invalidates all outstanding tokens,
which is covered in Rollout.

### Secret handling

Derive a dedicated key rather than reusing `AUTH_SECRET` directly, so the two
concerns can rotate independently and the digest key can be given a distinct
scope:

```ts
function lookupKey(): Buffer {
  return crypto.hkdfSync(
    'sha256', Buffer.from(process.env.AUTH_SECRET!, 'utf8'),
    Buffer.from('docmint:verification-token-index:v1'),
    Buffer.from('verification-token-index'),
    32
  );
}
```

Fail closed if `AUTH_SECRET` is unset — never fall back to an unkeyed digest.

## 3. Invariants preserved

| Invariant | How it survives |
|---|---|
| Secure token verification | bcrypt hash remains stored and remains the authority; HMAC only locates the row |
| Tokens not recoverable from DB | bcrypt hash at rest; HMAC digest is keyed and useless without `AUTH_SECRET` |
| Token-purpose separation | Explicit `purpose` column (§4) replaces the current `v_`/`r_` string-prefix check |
| Expiration | `expires > now` enforced in the lookup query and re-checked before use |
| Single use | Row deleted after success, unchanged. `tokenIndex` uniqueness additionally prevents two rows sharing an index |
| DoS resistance | O(1) indexed read replaces O(n) bcrypt — strictly better than the current cap |
| Generic failure response | `400` with the existing message for every rejection path |

---

## 4. Token-purpose separation

Today separation is a **string prefix on the presented token**: verify-email
rejects `r_`, reset-password rejects `v_`. That is adequate but indirect — the
purpose of a row is inferred from an untrusted input's shape.

The `purpose` column makes it explicit. Verification becomes:

```ts
if (candidate.purpose !== EXPECTED_PURPOSE) return reject();
```

Recommended values: `'verify'`, `'reset'`. Rows with `purpose = NULL` are
legacy and are accepted for **both** purposes during the transition window
(§5), matching today's behaviour where legacy bare-hex tokens are accepted by
either route.

The prefix check should be **retained** as defence in depth even after the
column exists — it costs nothing and stops a purpose-confused token before it
reaches the database.

## 5. Compatibility and rollout

### Compatibility

- **Existing rows** have `tokenIndex = NULL` and `purpose = NULL`. They are
  not readable by the indexed path.
- **Two options for legacy rows:**

  **A. Dual-path (recommended).** Try the indexed lookup first; if no row is
  found *and* the row count suggests legacy data, fall back to the bounded
  sweep. Correctness is restored immediately for every existing token. The
  fallback can be removed once all legacy rows have expired (TTL is 1 h for
  reset tokens; verification tokens should be checked in
  `src/lib/utils/constants.ts`).

  **B. Invalidate.** Deploy the column, let legacy tokens lapse, drop the
  fallback. Simpler, but logs out anyone mid-flow during the window and
  should not be done without a deliberate product decision.

- **Rotate `AUTH_SECRET`?** Only relevant if the derived key changes version
  (bump `v1` → `v2` in the HKDF `info` string). Rotating `AUTH_SECRET` itself
  already invalidates all Auth.js sessions in this codebase, so prefer a
  version bump over rotating the secret.
- **Backfill is impossible.** The raw tokens are not recoverable from bcrypt
  hashes, so legacy rows cannot be given a `tokenIndex`. This is the reason
  option A exists.

### Rollout

1. Add columns, nullable, no constraint beyond the indexes. Additive only —
   no data rewrite, no lock on `verification_tokens`.
2. Deploy code that writes `tokenIndex` + `purpose` on issue.
3. Deploy dual-path lookup (indexed first, bounded sweep as fallback).
4. After maximum token TTL has elapsed with no legacy rows in play, remove the
   fallback and the `MAX_TOKEN_CANDIDATES` sweep from both routes.

Steps 2 and 3 can ship together; 4 is a follow-up once TTL has passed.

### Migration SQL (written, **not applied**)

`prisma/migrations/20261010000000_add_token_index/migration.sql`:

```sql
ALTER TABLE "verification_tokens"
  ADD COLUMN "tokenIndex" TEXT,
  ADD COLUMN "purpose" TEXT;
CREATE UNIQUE INDEX "verification_tokens_tokenIndex_key"
  ON "verification_tokens" ("tokenIndex");
```

Nullable columns with no default: existing rows get `NULL`, no table rewrite.

> **This migration has NOT been applied to any environment.** It requires
> explicit approval and a deliberate deployment step. Rolling the code out
> before the migration is safe (the resolver handles the columns being absent
> only insofar as `safeTokenIndex` returns null and the fallback sweep is
> used), but rolling the code out after the migration and before the writer
> changes would leave rows without an index — which the fallback also handles.
> Both orders are therefore supported; see Rollout.

### Behaviour under each deployment state

| State | Behaviour |
|---|---|
| Migration applied, writer deployed | One indexed read, one bcrypt compare. No sweep. |
| Migration **not** applied | `safeTokenIndex` cannot persist an index → rows get `NULL` → bounded sweep fallback. Correct, just slower. |
| `AUTH_SECRET` missing | `safeTokenIndex` returns null; sweep fallback still resolves tokens. Signup and reset keep working. |
| Legacy rows already in the table | `tokenIndex = NULL`, `purpose = NULL` → sweep fallback; accepted by **both** routes, preserving the pre-change behaviour for tokens already sitting in users' inboxes. |

### Tests

20 tests covering: determinism, secret separation (a different `AUTH_SECRET`
yields a different digest), fail-closed on missing/short secret, the indexed
path performing no sweep, resolution beyond the old 50-row window, bcrypt
remaining authoritative, expiry rejection, purpose mismatch, legacy rows
accepted from either route, the fallback being capped at 50, no sweep for an
unknown token when the index is active, operation without `AUTH_SECRET`, and
`consumeVerificationToken` never throwing.

## 6. Regression tests

Added: `src/app/api/auth/token-lookup.test.ts` (16 tests, passing).

Covers the current behaviour and the invariants that must survive the change:

- **>50 valid token records** — builds a 120-row sweep with the real token at
  position 100 and asserts the current capped-window rejection. This test
  documents the defect and is the witness for the fix; it should be inverted
  to expect success once the indexed lookup lands.
- **Sweep bounds** — asserts `take === 50` and that comparison stops at the
  first match (11 comparisons for a match at index 10), pinning the DoS cap.
- **Purpose confusion, both directions** — a `r_` token rejected by
  verify-email and a `v_` token rejected by reset-password, each asserted
  *before* any database or bcrypt work.
- **Single use** — token deleted after success; replay finds nothing.
- **Expiry** — only unexpired rows are considered.
- **Session revocation** — reset increments `passwordVersion`.
- **Abuse resistance** — per-IP caps return 429 without re-entering bcrypt.
- **No consumption on failure** — a deleted account's token is not burned.

### Tests to add when the indexed lookup lands

- Indexed path resolves a token that sits beyond the 50th row.
- `tokenIndex` is unique — two rows cannot share a digest.
- Rows with `purpose = NULL` are accepted by both routes during the
  transition, then rejected once the fallback is removed.
- Digest is keyed: the same token under a different `AUTH_SECRET` produces a
  different `tokenIndex` and does not resolve.
- Missing `AUTH_SECRET` fails closed rather than using an unkeyed digest.
